### Added
- **Practices pack: core SDD implementation/review skills, secret-read and quota-window hooks, optional handover and marketing skill groups, and operating rules** (FEAT-037):
  - **Core SDD loop closed (`spec-implementer` and `pr-review`)**: Installed on every box (and synced additively on `biab update` via `48-user-content.sh` without overwriting any skill you have edited). Both target the box's v1 SDD layout (`status`/`validated_by`, `§0–§6` or Starter `Summary`/`Tasks`/`QA`), work in isolated git worktrees (`git worktree add`), record progress in the pull request body, and stop at the pull request by default so the merge stays yours (with a read-only owner switch at `~/.config/buildersinabox/sdd.json` `.auto_merge`).
  - **Core hooks (`biab-secret-guard.sh` and `biab-quota-window.sh`) + shared 4-CLI secret-read guard + Antigravity parity** (FEAT-037, FEAT-044): `payload/hooks/secret-guard-rules.sh` is the single source of truth for 10 secret-path rules (`.env` and `.env.*`, `~/.ssh` private keys, `.claude/secrets/`, `.codex/auth.json`, `/secrets/*.env`, `.credentials.json`, `creds.json`, `/etc/buildersinabox/paseo.env`, `.gemini/antigravity-cli/antigravity-oauth-token`, `firestore.rules`, tested across `payload/hooks/tests/secret-guard-corpus.tsv`). Safe templates (`.env.example`, `.pub` keys) and `git commit -m` messages pass. Claude Code (`biab-secret-guard.sh`) and Antigravity (`biab-secret-guard-agy.sh` on `run_command|read_file|view_file`) ask interactively and deny in unattended mode; Codex (`biab-guardrail-codex.sh`) denies secret-file reads; OpenCode gates them through its seeded `permission.bash` rules. `biab-quota-window.sh` and `quota_watchdog.py` check your 5-hour rolling window burn rate from local Claude Code and Antigravity transcripts and nudge only when pace is hot. Antigravity's `biab-guard` plugin (`payload/hooks/agy-plugin/hooks.json`) wires `biab-guardrail-agy.sh`, `biab-secret-guard-agy.sh`, `biab-format-agy.sh`, and `biab-specs-agy.sh`, and skill symlinks are created across all four discovery directories (`.claude/skills`, `.gemini/skills`, `.gemini/antigravity-cli/skills`, `.gemini/config/skills`).
  - **Skill groups in `biab add <skill-or-group>`**:
    - `biab add handover` installs `agent-handover`, `wrapup`, and `unwrap` for repository-aware task handovers across sessions and AI CLIs.
    - `biab add hotfix`, `biab add fact-checker`, and `biab add verify-frontend-change` install individual optional skills.
    - `biab add marketing` installs 19 MIT-licensed marketing skills from `coreyhaines31/marketingskills` (pinned in `payload/skills/marketingskills.lock.json` with `LICENSE.marketingskills` and per-skill `LICENSE` copies; upstream `product-marketing` renamed to `marketing-context` so BIAB's core `product-marketing` advisor stays intact).
  - **Operating rules (`payload/docs/operating-rules.md`)**: Documents what agents do without asking, the six hard stops (money, credentials/security configs, external actions on your behalf, irreversible deletes, production deploys, `sudo`), parallel work with `git worktree`, and why local hooks are brakes while GitHub branch protection is the lock.
- **A shell-command guard on Antigravity, Codex and OpenCode, and an honest table of what each AI CLI gets** (FEAT-042). Until now only Claude Code had hooks that refuse destructive shell commands (`rm -rf /`, `mkfs`, `dd` to a disk, a fork bomb, `curl … | sudo bash`, a force-push to `main`). The patterns now live in one place and each CLI's guard is built from them, with a test corpus that pins every decision. What each CLI gets, stated so it does not promise more than the code declares:
  - **Claude Code**: the guard with confirm prompts, as before, plus hooks, the status line and the night shift. Its behaviour did not change; the hooks merge is now safer (an invalid or symlinked `settings.json` is left alone, and the write is atomic).
  - **Codex**: the same patterns, registered in `~/.codex/hooks.json` as an additive entry that never touches your own hooks. **It needs your approval once**: run `codex`, type `/hooks`, approve it. Until then `biab status` says PENDING APPROVAL and Codex skips it, `codex exec` included; the wizard's last screen says so too. It refuses but never asks (Codex's own approval rules decide the confirm-class commands). No night shift yet.
  - **Antigravity**: the same patterns and confirm prompts, installed as the `biab-guard` plugin in `~/.gemini/config/plugins/biab-guard` (with its own `hooks.json` so your `~/.gemini/config/hooks.json` is never opened). No night shift: its command-line mode waits for a terminal that an unattended run does not have, and it cannot log in without a person at a screen.
  - **OpenCode**: a **partial** guard, deny rules appended to `permission.bash` in your `opencode.json` (never changing one of your keys), covering a smaller set than the other three: it cannot see a pipe, so `curl … | bash` is not covered, nor are quoted targets, `rm -rf /*`, `bash -c`, a fork bomb, or a command that starts with something else (`sudo` before a force-push, `env`, `VAR=1 rm`). Subagents obeying them is not confirmed, and a project's own `opencode.json` that allows everything overrides them. No night shift.
  - **`biab status`** prints, for your box's CLI, what it has: phone app, guard (with its state: active, pending approval, switched off, partial, none), and the night shift with the reason when it is not there.
  - **The README table is generated** from the adapters' declared capabilities (`biab-guard matrix`), and a test fails if the README differs from them or if a README, site or SECURITY line claims a guard, confirm prompts or full coverage a CLI does not declare. The landing page no longer says the practice "works the same either way".
  - **Switching it off**: `touch ~/.biab/hooks-disabled` (or `BIAB_HOOKS_DISABLED=1`) stops Builders in a Box from adding a guard and silences the script guards; OpenCode's rules already in the file stay until you delete the keys `bash /opt/buildersinabox/payload/hooks/opencode-guard.sh keys` prints.
  - **What is checked and what is not**: registration, the hooks list Codex reports, the generated keys against the real OpenCode engine, the merge into your files and the status text are all tested. Watching each guard refuse a command in a real logged-in session on a real box is a hardware pass still to be done, and none of this is a claim about a live session until then. Known gaps in the shared pattern list (`rm -Rf /`, `git push origin +main`, a command in backticks, and a few more) are listed in the test corpus and unchanged.
- **OpenCode is the fourth AI CLI** (FEAT-040, wave 1): pick it in the installer or the wizard next to Claude Code, Codex and Antigravity. It is installed from a pinned release (v1.18.31, `linux-x64`, or the `baseline` build on a CPU without AVX2) whose sha256 is checked before anything is written, into `/usr/local/bin/opencode`; a copy of `opencode` earlier on your PATH stops the step instead of silently winning. You sign in with `opencode auth login` (an OpenCode Go or Zen key from opencode.ai/auth, or another provider); a login you cancel leaves the setup paused, and `biab` resumes it. It reads the bundled skills from `~/.agents/skills` directly. **In the Paseo app it asks before it edits files, fetches pages or runs shell commands only because Builders in a Box writes those rules** in `~/.config/opencode/opencode.json` (OpenCode allows everything by default), and only while that file still says so; otherwise it stays reachable over SSH and the wizard says which rule is not holding. **No night shift for OpenCode**, and no hooks or status line: that is deliberate. `--uninstall` removes the binary only if Builders in a Box installed it. Still to confirm on real hardware: a real login and the permission prompt in the app (`HARDWARE-PASS.md`).
- **`/first-project` takes your idea all the way to a pull request** (FEAT-036, phase 1). It used to scaffold a folder and stop; now it offers the templates in the box's catalogue (`payload/templates/projects/manifest.tsv`, read through the new `biab-project` script, so adding a template is a directory and a manifest line) or "describe your own idea", writes the first spec with you through `/sdd-coordinator` before any code, builds it on a branch from `main`, and opens a pull request on your GitHub — private, and the merge is yours. If GitHub is out of reach (no `gh`, not logged in, no network, a repository name already taken, a rejected push) it keeps spec, code and branch on the box and says what is waiting. Say `/first-project` again at any point and it resumes at the step the files on disk say you reached, never asking again what the spec already holds, never overwriting a file of yours and never discarding unsaved work; after you merge it says the walk is complete. `/tutorial` and `/whats-ahead` read the same catalogue and progress. `/second-project` now creates its own project through the same script (it used to look for a spec that only existed if you had picked the second option on day one), and the personal finance app, which needs a cloud account and a domain, is reached from there and not offered on day one. The `.biab/dev-check.sh` placeholder (exit 3, "not configured") is now written by `biab-project`. `--uninstall` now says outright that your projects and the walk's progress stay with your home directory. A code skeleton whose dev check already passes, for the night shift to merge on the first night, is the second phase of FEAT-036.
- **Every tool BIAB installs is pinned, and a weekly bot keeps the pins fresh** (FEAT-038). Claude Code and Codex used to be an unpinned `npm install -g` that never upgraded; they are now installed from a committed lockfile (`payload/pins/`) into `/opt/buildersinabox/tools`, and `biab update` moves a box to the version this release was tested with, replacing a different installed one (newer too: the pins were tested together). A copy of Claude Code or Codex that an earlier BIAB installed with `npm install -g` is removed so the pinned one is the only one; a copy you installed yourself is left alone and reported. Claude Code is installed without running its install script (the platform binary comes from its locked optional dependency and is checked by the lockfile hash), so no third-party script runs as root.
  **`biab update --latest`** installs the newest stable release of Claude Code, Codex, Paseo and agy instead of the tested ones. It prints that this combination is untested and unsupported before it installs anything, never picks a pre-release, and marks the box OFF-PIN: `biab status` and `/morning-check` say so, with `biab update` as the way back. Run `biab update` once first on a box from before this version, or `--latest` is ignored by the old command and you get a normal pinned update.
  **`biab auto-update on [weekly|daily|monthly|'Mon 03:30']`** is an opt-in timer that runs `biab update` (never `--latest`); it is off until you turn it on, and `off` or `--uninstall` removes it. Because it runs plain `biab update`, a box that went off-pin with `--latest` goes back to the tested versions at the next run. `--uninstall` now also removes the `claude` and `codex` links into the pinned tools tree (a `claude` or `codex` you installed yourself is left alone).
- **The night shift can go past the pull request: a reach ladder** (FEAT-039). `sudo biab-night-shift arm --reach pr|dev|main`, and `dev` is the default for a new arm. At `dev`, once the agent has exited, the runner merges its pull request into a `dev` branch only if every gate passes: the PR is the one it opened tonight, it touches no danger zone (CI config, `.biab/`, secrets, infrastructure, migrations, auth, payments, dependency manifests, agent instruction files, deletions, more than 60 files or 2,000 lines), CI is green, an independent review — a second call to your CLI with no tools, judging the diff against the spec — finds nothing blocking, and your `.biab/dev-check.sh` passes on the merged result. Anything missing or unclear stops at the pull request, and the morning summary names the step. `main` reach merges into your default branch after the same gates and needs you to type `UNLOCK MAIN`.
  **What is a lock and what is a brake, per level.** At `pr` and `dev`, nothing reaches your default branch without your approving review: that is branch protection, checked before a pass spends anything. The merge into `dev` is a brake, not a lock — the agent and the runner share your account and token, so it rests on the hook and on the runner merging only after the agent has exited, pinned to the commit the gates saw. At `main` nothing is a lock.
  **Cost:** $2.50 per pass at `dev`/`main` ($2.00 implementation + $0.50 review), one hour of wall clock as before. A box armed before this version keeps stopping at the pull request until you arm it again.
  New operator commands run as you, never as root: `biab-night-shift dev-setup <project>` creates and protects `dev`, `dev-sync <project>` brings it up to date with `main`, `promote <project>` opens the `dev` → `main` pull request and prints a merge-commit command. `/first-project` now writes a `.biab/dev-check.sh` placeholder that exits 3 ("not configured") and asks how you run the project; `/morning-check` shows the last pass. The PreToolUse guard now also blocks pushes to `dev`.
- **Paseo is the default interface on every box** (FEAT-035, extended to Antigravity by FEAT-041). The box runs a pinned Paseo daemon as the root-owned systemd service `biab-paseo.service`, bound to your Tailscale address only with the relay off, and the last wizard step starts your first agent in a workspace named "BIAB · ai-platform" and walks you through pairing the Paseo app. `/first-project` adds a "BIAB · <project>" workspace per project instead of a tmux session. A watchdog restarts the daemon with a retry cap and `biab status` reports a daemon that could not be brought back; if you skip pairing, `sudo biab paseo pair` (and `--rotate`) prints the three values later, and `sudo biab paseo restart` clears a give-up. If Paseo is down, SSH over Tailscale into your AI CLI still works and `biab status` prints the command.
  **Antigravity runs in the app too, asking before it runs commands, writes files and reads outside the project** (FEAT-041, next bullet): Paseo's own Antigravity plugin always starts `agy` with `--dangerously-skip-permissions` (Builders in a Box never passes it), so it is switched off and Builders in a Box declares its own provider instead. `biab update` on a box installed with the tmux layout registers one Paseo workspace per existing project and removes nothing, and never prints the phone password (`sudo biab paseo pair` does, in a terminal only, to avoid leaking it into a transcript; this is not a defence against agents on the box); your directories and live tmux sessions are untouched. `biab status` is now a short summary; `biab status --json` is the previous output, unchanged.
  `--uninstall` stops and removes the daemon, its units, its pinned tree and its credential, and removes `~/.biab/paseo` only when it carries our ownership marker — a `~/.paseo` you already had is never touched.
- **Antigravity in the Paseo app, with permission prompts** (FEAT-041, which replaces the full-access consent step drafted under FEAT-035 R11 before it was ever released). The wizard starts your first Antigravity agent in the app, opening the tutorial, exactly as for Claude Code and Codex; there is nothing to type or switch on. The agent runs through a provider Builders in a Box declares itself, the pinned `agy` as `agy acp --disable-telemetry --add-dir <home>/.agents/skills` (Antigravity's Agent Client Protocol mode), where a request to run a shell command, write a file (in the project, home, `~/.biab` or `/var/tmp`) or read outside the project reaches the app and waits for your answer (measured with `agy` 1.4.11; see the Security notes).
- **Opt-in night shift** (`biab pack add night-shift`): at 03:00 the box picks one spec you have already validated, implements it with your AI CLI, and stops at the pull request. Validated spec at night, pull request in the morning, on hardware you own.
  **It spends your subscription unattended, so it is switched off twice over.** Installing Builders in a Box schedules nothing; adding the pack installs a *disarmed* timer that only simulates — `biab-night-shift run` names the spec it would pick and spends nothing. Real passes need `sudo biab-night-shift arm`, which prints the per-pass cap ($2.00), the one-hour systemd timeout and your last seven days of spend **before** asking you to type a confirmation word. `disarm` stops the spending without uninstalling anything, and `BIAB_NIGHT_SHIFT_DISABLED=1` or a sentinel file skips a night.
  At `pr` reach it stops at the pull request (see the reach ladder above for `dev` and `main`). A `PreToolUse` hook, loaded from the command line so the agent cannot remove it by editing its own settings, allows only `git push [-u] origin <feature-branch>` and a handful of `gh` verbs, and blocks merges, releases, pushes to main, the GitHub API, CI edits, root and eval — from the shell and from the file-editing tools, with MCP switched off for the pass. That is a brake; the lock is branch protection on your repository, which a real pass checks for before spending anything (see *Security* below). It also refuses to run on a dirty working tree, takes one spec per night with no retries, and will not re-attempt a spec for 14 days — the brake that stops an ambiguous spec becoming a recurring bill.
  Today only Claude Code can be armed (arming requires a headless mode, a spend cap and a mechanical tool guard); on Antigravity or Codex the pack installs and simulates, and tells you so when you add it rather than when you try to switch it on.
- **The browser pack can finish a form, and gets past sites that refuse a headless desktop browser.** `biab-browse run <url> < workflow.json` runs up to 20 `fill`/`click`/`select`/`wait_for`/`read_text` actions in one browser, on one page, in order, stopping at the first failure. Until now a multi-step task meant one `biab-browse open` per step and each call closed the browser, so filling a field and then submitting it submitted an empty form. The workflow arrives on stdin rather than as an argument, so a password inside one is not visible to anyone who can list processes, and is staged in a root-owned directory the browser engine can read from but not write to.
  It also picks how to open the page. A pilot on this stack measured Reddit and Sephora serving a 403 to desktop headless while the same Chromium, told it was an iPhone, got a 200 — so the default `--mode auto` tries desktop headless, then iPhone emulation, then a headful browser on a temporary virtual display, and says on stderr which one worked. `--mode desktop|iphone|headful` pins one.
  **It is a fallback, not a retry loop, and not evasion.** Modes only ever switch *before* the first action, so a click or a form submission is never replayed against another mode. A CAPTCHA does not trigger a fallback (nothing up the ladder solves a challenge), and neither do timeouts, 404s, 429s, 5xxs or login walls — those are real answers from the site and are reported as themselves. There are no stealth patches, no proxy rotation and no CAPTCHA solving, and iPhone mode is documented as Chromium emulation, not Safari.
- The AI-CLI registry gained an `unattended` capability and an `ai_cli_unattended_cmd` verb, so what a box may do unsupervised is declared once in its adapter instead of inferred from the CLI's name.
- The browser pack's test suite grew 44 cases for the above (25 to 69): the mode ladder and its exit codes, a local fixture server that serves a 403 interstitial to a desktop user agent and the real page to an iPhone (so the claim is pinned deterministically instead of depending on a third party's mood), a multi-step workflow proving page state survives across actions, a failing action proving the ones after it do not run, and the full workflow schema — including that an article containing the words "access denied" is not mistaken for being denied access.
- `payload/test/uninstall-contract.sh` grew eleven cases (`NS-1`…`NS-11`) covering everything the night shift leaves outside `/opt`: both systemd units, the runner, the file that authorises spending, the state tree and the guard directory — including that the timer is disabled before its unit file is deleted, that `daemon-reload` comes afterwards, and that a stranger's timer in the same directory survives byte-identical.

### Security
- **The Paseo phone password is not protection against your own agents.** It lives in `/etc/buildersinabox/paseo.env` (`root:root`, `0600`), never in state, logs or the repo, but it has to be in the environment of the Paseo processes, so any agent running as the box user can read it from `/proc/<pid>/environ`. This is documented in `SECURITY.md` and the README security model. The bind address, relay switch and password sit in a root-owned unit, so the agents cannot loosen them through `~/.paseo/config.json`.
- **A workflow is staged where the browser user cannot reach it.** Caught in review before release: the first version of `biab-browse run` wrote the workflow into a directory under `/var/lib/biab-browser`, which the browser user owns. Write permission on a directory is what governs rename and unlink — whoever owns the entry — so the browser user could have replaced the path with a symlink in the window between root creating the file and root writing to it. `chmod`, a `>` redirect and `chown` all follow symlinks, so that would have let a Chromium sandbox escape truncate a root-owned file of its choosing and then be handed ownership of it, defeating the dedicated unprivileged user that exists to contain exactly that. The workflow now lives in `/run/biab-browser` (root-owned, mode 0711, cleared on reboot and on uninstall), stays owned by root, and is only group-readable by the browser user, which is all the driver needs. The pack's other directories keep their existing ownership: there the browser user writes and root only reads back, with the recheck that has guarded the screenshot handoff since 0.2.0.
- **Night shift: the no-merge guard is a whitelist now, and branch protection is the lock.** The first guard was a blacklist of seven spellings; a battery of 27 ways to merge, push to main or deploy walked past 22 of them (`git push` with no refspec while on main, `git push origin "main"`, `gh api -X PUT …/merge`, `gh workflow run deploy.yml`, `curl` with `gh auth token`, a workflow file edited with the Write tool…). The guard now allows only `git push [-u] origin <feature-branch>`, `gh pr create` and a few read-only `gh` verbs; blocks the GitHub API, HTTP clients against github.com, credential reads, `git remote`/`git config`/`git tag` tampering, edits to `.git/` and `.github/workflows/` (shell and file tools), `sudo` and `eval`; and the pass runs with `--strict-mcp-config --disallowedTools mcp__*` so a GitHub MCP server cannot hand the agent a merge tool the hook never sees. A security review of the rewrite added what a lexical guard also has to see: quoted verbs (`git "push"`), git/gh environment overrides (`GIT_CONFIG_KEY_0=remote.origin.url…`, `GH_REPO=`), shell functions and aliases, writes to `~/.gitconfig` and `~/.config/git/`, reads of credential stores through the Read/Grep tools, the repository's real default branch (not just `main`), and rulesets with bypass actors. What it still cannot catch — a script written to disk and then executed, or a variable holding the word `git` — is why a hook is a brake and not a lock; and the lock covers merging into *your* repository, not pushing the code somewhere else, which only the hook guards. The lock is a required review on the default branch, which the agent, acting as the owner, cannot give itself: a real pass now asks GitHub (classic protection or rulesets) before spending anything and aborts with `default-branch-not-protected` if it is missing; `sudo biab-night-shift arm --unprotected-ok` accepts running without it, root-owned like the mode file, and the morning summary flags every pass that ran that way. README, landing page, installer and `arm` copy no longer claim "can't merge without you" on the strength of the hook alone.
- **Antigravity's permissions are a default with known limits** (FEAT-041). Paseo's per-agent Auto Accept switch stops that agent asking, as Bypass does for Claude Code and Full Access for Codex; Builders in a Box never turns it on, but Paseo's unattended runs (schedules) do by default and the pinned Paseo has no way to remove it. Antigravity's provider settings are a file of your user, like the permission settings of Claude Code and Codex: at every daemon start Builders in a Box puts the safe ones back (or the service refuses to start), and `biab status` says when they changed since. It does not watch or undo changes while the service runs, and `agy`'s own configuration (`~/.gemini/antigravity-cli/settings.json`, `hooks.json`, `~/.gemini/config/projects/`, a workspace's `.agents/`) is outside the guard. See `SECURITY.md`.

### Changed
- The Antigravity CLI (`agy`) pin moved from 1.1.0 to 1.4.11 (new sha256 pin). The 1.4.2 release this branch used before has no `acp` subcommand, which the Paseo provider needs; `46-paseo.sh` checks `agy acp --help` before it writes a unit or a config and stops with a clear message otherwise, leaving SSH and the bare CLI working.
- **Antigravity boxes move to Paseo on `biab update`** (FEAT-041). A box on SSH + terminal sessions gets the daemon and one workspace per project; its running terminal sessions and `~/.tmux.conf` are left alone. A box that had switched on the earlier full-access mode is moved to the provider that asks, its directories and workspaces are kept, and it is told once what Antigravity now asks about (shell commands, file writes in the project, home, `~/.biab` and `/var/tmp`, reads outside the project; not reads inside the project, web search or fetch, or writes in `/tmp`). Conversations started in the old mode stay visible in the app but cannot be continued: start a new agent. `sudo biab paseo antigravity` remains until 2027-04-30 only to print that notice.
- Paseo's own Antigravity provider is disabled on every box, so the full-access provider is not offered in the app.
- **Antigravity asks before it reads outside the project** (FEAT-041, measured with `agy` 1.4.11 through `agy acp`). The `antigravity-acp` provider now runs `agy acp --disable-telemetry --add-dir <home>/.agents/skills` and the agy settings seed has `allowNonWorkspaceAccess: false`: with `true`, agy read any file outside the project without asking, and it never asks before a web search or fetch, so a silent read plus an unasked fetch could carry files out. Reading a skill from the skills folder still does not ask. The first `biab update` changes an existing `true` to `false` as your user (no links followed, other settings are kept), tells you once and records a mark in the box state, so it never touches the setting again and a `true` you set later is yours; a symbolic link or a file that is not a JSON object is left alone with a warning that names the file and the line to set by hand. Measured and now documented: it asks before shell commands, file writes in the project, home, `~/.biab` and `/var/tmp`, and reads outside the project; it does not ask before reads inside the project, web search, web fetch or writes in `/tmp`; the prompt offers only allow once or reject, with no always-allow, and the Auto Accept switch is separate.
- `payload/test/uninstall-contract.sh` and the new `payload/test/paseo.sh` cover the Paseo teardown (stop-before-delete order, an unmarked home surviving, a second pass) and the daemon's pin, units, credential, watchdog and migration. Re-installing with a new pin removes the older pinned tree.
- `extend-yourself` no longer claims linger is enabled at first boot. It only is on the USB/ISO path; after a `curl | sudo bash` install a user-level timer stops firing as soon as your last session ends, which is why the night shift ships a system unit instead.
- The starter spec template carries a `validated_by` field. Without it, a box in starter mode could never produce a spec the night shift was allowed to pick up — the feature would have been unusable out of the box.
- The scaffold never replaces a hook you already had. Registering our hooks into `~/.claude/settings.json` is now additive for every event: `PreToolUse`, `PostToolUse` and `Stop` used to be treated as ours to own and overwrote whatever you had configured there. Your hooks stay, ours run alongside them, and re-running the scaffold still adds no duplicates.

### Removed
- **The Antigravity full-access opt-in** (FEAT-041): the typed `full access` phrase, `sudo biab paseo antigravity on|off`, `BIB_ANTIGRAVITY_PASEO`, the `paseo-optin` capability and the `biab-paseo-antigravity` helper. Antigravity under Paseo no longer has a mode that runs every tool without asking.
- **tmux on new installs** (FEAT-041): nothing installs it, creates a session, copies `~/.tmux.conf`, adds the `tmuxc` helper, auto-attaches at login or offers a terminal-session branch in `biab-workspace`, and no text on a new box mentions it. Existing boxes keep their tmux package, sessions, `~/.tmux.conf` and `tmuxc`; the code that reads the old layout on update carries a sunset (2027-04-30 earliest).

- `biab status` no longer says the Antigravity provider settings "changed since the service started — run: sudo biab paseo restart" while the daemon is still waiting for the tailnet (there is no `config.json` until it starts). The launcher's refusal for a symlinked `agy` now says "is a symbolic link".
- A workflow piped into `biab-browse run` is no longer silently truncated. The wrapper slurped stdin with `dd bs=65537 count=1`, which issues a single `read(2)` — and a read from a pipe returns only what happens to be buffered right then. Measured: a payload written in two chunks 300ms apart arrived 36 bytes short with no error at all, leaving the caller to puzzle over "invalid workflow JSON"; a cut that happened to stay valid JSON would have *run*, short.
- An unknown `--mode` reported the wrong exit code. `mapfile -t attempts < <(browser_mode_attempts "$mode")` reports `mapfile`'s status and never the process substitution's, so the `|| exit $?` guarding it was dead code: the run ended up exiting 6, the code reserved for "the site blocked us", instead of 2 for a usage error.
- A failed merge can no longer cost you your `~/.claude/settings.json`. The scaffold read and rewrote the file in one step, so if the merge errored the file was truncated to a blank line — taking unrelated settings (`env`, `apiKeyHelper`, and the rest) with it. It now leaves the file untouched and warns instead.
- The hooks + scaffold-seed test suite (`payload/hooks/tests/run-tests.sh`) now runs in CI and actually exercises the scaffold. It had been aborting partway through for some time, skipping roughly 40 later assertions — red, with nothing running it to notice.
